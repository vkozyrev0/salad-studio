## 3. The cause: the group had been idle-stopped, and this request started it

> **Forward note (2026-10-14):** the start path this document analyses was
> removed on 2026-10-13 (commit `d52907b`). The queue no longer starts a
> container: a group that is not running is refused, with the profile and its
> gateway named, so the press reports the container is down instead. The
> idle-stop and ownership analysis below still holds; only the start does not.

The restart is a **fresh container after an idle stop**, triggered by this
request's dispatch. The chain, each step cited:

1. The previous render finished at `2026-09-27T22:10:41.680709+00:00`
   (`[INFO] Prompt executed in 15.63 seconds`), and the queue's record for that
   job is `finished_at` 1790547041.9724004 = 22:10:41 UTC. That is the last
   activity the app had for this container.
2. The container sat idle for the app's one-hour timeout
   (`salad_studio/studio-metadata.json` → `{"idle_stop_s": 3600}`;
   `studio_meta.DEFAULT_IDLE_STOP_S = 3600`; no
   `~/.config/salad/studio-metadata.json` override), and the app's 15-second tick
   (`app.py` `_poll_salad_status` → `_run_idle_check`) stopped it:
   `23:10:53.614` − `22:10:41.972` = **3611.6 s**, one tick past the 3600 s
   deadline. Salad's own `finish_time` 23:10:53.395 confirms the stop.
3. At 01:05:42 UTC the press entered the queue on line `klein`;
   `SaladQueue.ensure_container` read the group's state, found it stopped, and
   POSTed `…/containers/flux2-klein2/start`. `salad_queue.py` logs that as "asked
   Salad to start …", and the ledger it wrote at 01:05:44.738 / 01:05:46 carries
   `"started_by_app": true` for `klein`. The group has `"autostart_policy":
   false`, so nothing else was going to start it.
4. Salad allocated `bd11da0a` and ran the whole cold boot: image pull, `klein
   prefetch: 4 files in parallel` (the unets, text encoder and VAE), then ComfyUI
   — "ComfyUI fully ready in 9.1s" at 01:12:56.153, **7 min 14 s** after the
   press. The earlier boot of this session cost more: 45 min from press to first
   plate (21:16:53 press → 22:10:41 render).

Why the ledger proves the record was re-created rather than merely touched: a
successful stop runs `_forget`, which drops the container's record; the
`last_active` written at 01:05:44.738 is a fresh adoption (`adopt()` sets
`last_active` when the name is new to `_owned`), and `started_by_app: true` is
written only by the start path in `ensure_container`. `_note_activity` would have
written a `finished` row for the same moment, and there was none at 01:05:44. So
the record's own values date the app's start to 01:05:44–01:05:46.

## 4. The trigger, against the request

Measured gaps, all from the captured lines:

| Event | Time (UTC) | Gap from the press |
|---|---|---|
| press (`studio-prompt-history.json` newest `ts`) | 01:05:42 | — |
| ledger fresh adoption (`last_active` 1790557544.7389045) | 01:05:44.738 | 2.7 s |
| `Container Group Started` (Salad) | 01:05:46.0627885 | 4.1 s |
| `Instance Allocated` `bd11da0a` | 01:08:06.2499707 | 2 min 24 s |
| `Instance Running` and prefetch of 4 files | 01:08:51.97 | 3 min 10 s |
| `ComfyUI fully ready in 9.1s` | 01:12:56.153604 | 7 min 14 s |
| startup probe `"url": "/health"` answered 200 | 01:30:51.834955 | 25 min 10 s |
| first readiness probe of the 10 s stream | 01:31:01.836494 | 25 min 20 s |
| `POST /prompt` reaches the container | 01:31:13.171047 | 25 min 31 s |
| `[INFO] got prompt` | 01:31:31.404714 | 25 min 49 s |
| `[INFO] Prompt executed in 14.91 seconds` | 01:31:46.311947 | 26 min 4 s |
| queue row id 113 `accepted` 200 | 01:31:47.494713 | 26 min 5 s |

The press-to-start gap is 4 s, and the start line is the platform's own record of
the `POST …/start` the app sent for this job, so the restart ties to the request.
What in the request preceded it is the routing and the container choice: a `klein`
graph (flux-2-klein-base-9b-fp8 at 1568×1264, 6 steps, cfg 1) whose checkpoint
only profile `klein` lists, pressed with the `klein5090` form selected, so the job
woke `flux2-klein2` (apple-gadogado) rather than the stopped `flux2-klein-5090`
(beet-ginger) the form named.

**The second cost: 18 minutes of gateway 503 after the container was up.** ComfyUI
was ready at 01:12:56.154, yet the app's first successful `POST /prompt` is
01:31:13.171 — 18 min 17 s later. Over that gap the gateway answered 503 ("503
Service Unavailable - SaladCloud") to every probe from this machine (01:16:07,
01:19:24, 01:19:56, 01:20:27, 01:20:59, 01:21:30, 01:22:02), and the app treats
503 as "container not up yet" (`salad_queue.BUSY_CODES`), so it kept waiting. The
container itself served only three requests in that time — `"url": "/ready"` at
01:17:21.911867 and 01:18:30.924935 (both `"statusCode": 200.0`), then
`"url": "/health"` at 01:30:51.834955 — and Salad's instance record stayed

```
"id": "bd11da0a-8400-4be7-96f1-c8ed5789c182",
"state": "running",
"ready": false,
"update_time": "2026-09-28T01:08:55.9331005+00:00",
```

with `update_time` never advancing past the allocation. The gate opened with the
probe sequence the group's own policy predicts: the startup probe
(`"path": "/health"`, `"initial_delay_seconds": 1200`, `"period_seconds": 120`,
`"failure_threshold": 20`) passed at 01:30:51.835, and the readiness probe stream
(`"path": "/ready"`, `"period_seconds": 10`) began 10 s later at 01:31:01.836 and
has continued every 10 s since; the app's own probe then succeeded and the POST
followed at 01:31:13.171. The 20-minute startup delay is measured from the
instance's allocation (01:08:06), so Salad does not ask the container whether it
is up until roughly 01:28, whatever the container has already done; the capture
holds a single `/health` line, so the first probe's exact instant is not in the
log.

**The render.** The job itself was quick once it was let through: the LoRA fetch
took 18.21 s, ComfyUI reported `[INFO] got prompt` at 01:31:31.404714 and
`[INFO] Prompt executed in 14.91 seconds` at 01:31:46.311947, and the queue
recorded `"state": "accepted", "status": 200` for id 113 at 01:31:47.494713. The
press's prompt-history row now carries its plate
(`studio-prompt-thumbs\1790557542.jpg`). So the request rebooted the container in
the sense that it paid for a full cold start of a stopped group — image pull,
30 GB of model prefetch, ComfyUI boot, then the platform's 20-minute startup-probe
delay before the gateway would route — and the render itself was 15 s.

## 6. Limitations

- The Studio log is in-memory only (`studio_log.format_line` feeds the Tk widget;
  the package has no file handler), and the app run captured in this session
  wrote nothing to stdout, so the app's own "asked Salad to start klein" and
  "stopped klein after 3600s idle" lines are not quotable from disk. The stop and
  the start are dated from Salad's lines and the queue ledger instead.
- The stop at 23:10:53 is attributed to the app on timing and on the ledger's own
  re-created record. A stop issued by hand in the Salad portal would look the same
  in the log stream; the 3611.6 s interval after the render, against the app's
  documented 3600 s timeout and 15 s tick, is the evidence for the app.
- The 18-minute gateway 503 window is bracketed by the container's `/health` and
  `/ready` lines, which is what the log-entries API carries. Salad does not log
  the gateway's ready-set decisions, so the reading above (startup probe gates the
  readiness probe, which gates the gateway) is the reading the probe timings and
  the group's own probe policy support, and the instance's `ready` flag is
  recorded from the API as it stood at 01:24.
- Retention held: a pull from 19:00Z shows nothing before
  `2026-09-27T21:16:59.9481172+00:00 [] {"message": "Container Group Started"}`,
  so the whole session is inside the retained window.
